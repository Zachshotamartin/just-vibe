# Composed workflows and reviewed coordination

Preserve the complete request, constraints and current authorization. These are phase contracts, not a requirement to create paperwork or workers. A small change stays in one direct workflow. `/orchestrate <request>` chooses the applicable contract; `/build`, `/fix`, `/refactor` and `/plan` can use the same contracts without another invocation. Do not create a goal unless the user requested one. Worker delegation requires the user's authorization and the host's permission rules.

## Phase contracts

| Flow | Inspect and decide | Implement | Verify and finish |
| --- | --- | --- | --- |
| Feature | Trace the existing user/API path, ownership and failure states. Define observable acceptance criteria, compatibility and rollout constraints. Use plan, arch-feature, api-design (consumer-visible operations) or arch-contracts (contracts between services or modules) when that decision is relevant. | Build a vertical slice through data, backend and UI. Use backend, database, React or UI workflows for the actual layers. Serialize shared contracts before dependents. Include loading, empty, error, keyboard and cancellation behavior when applicable. | Exercise the representative user path and a meaningful failure path. Check compatibility, accessibility and security at changed boundaries. Review actual diff, resolve findings, and report evidence. Deploy only when requested. |
| Fix | Reproduce the reported failure or identify precisely why it cannot be reproduced. Trace input to the failing boundary; inspect regression history only as relevant. Distinguish cause from symptom. | Implement the smallest correction that preserves existing contracts. Add a discriminating regression check when useful; avoid unrelated restructuring. | Show that the reproducer fails before and passes after when feasible, and check nearby callers or boundary cases. Unreproduced suspicions remain labeled; do not claim a test was run from reading it. |
| Refactor | Name the behavior to preserve, affected callers and a reversible seam. Capture current contract evidence and performance constraints. | Move one responsibility at a time, maintaining compatibility or an explicit migration. Keep semantic changes separate when they would obscure the refactor. | Compare observable behavior and contracts; run relevant tests and measure performance only when at risk. Review the integrated result, remove dead paths only with evidence, and explain any remaining migration. |
| MVP | Define the user, one valuable end-to-end path, explicit non-goals, data ownership and a usable completion criterion. Resolve the irreversible architectural choices; use reversible defaults for the rest. | Ship the smallest working vertical slice, including persistence and recovery that the product actually needs. Use fixtures only when clearly labeled and allowed by the request. Do not silently replace required integrations with fake data. | Run the core path in the browser or client, its main failure path, and persistence/reload checks. Report missing credentials or service dependencies precisely. Separate a working local product from public deployment. |

At a phase boundary record what was produced, its checked version and the next dependency. Use an existing goal, task evidence or a concise working note; do not duplicate all three. Completion means the requested implementation works with supporting evidence, not that all phase labels were traversed.

## Dependent workers

Native tools: `orchestration_read`, `orchestration_manage`, `workers_read`, `workers_manage`, `workers_result`, `workers_verify`, `workers_apply`. Native writes and workers must both be enabled. CLI equivalents use `just-vibe orchestrate <operation> --stdin --root <project>` and `just-vibe workers <operation> --stdin --root <project>`; provide one JSON object on stdin. Read current revisions before mutations.

1. Explicitly enable workers through `workers configure` or guided setup. Configuration is opt-in; it does not authorize an assignment. `workers status` reports revision and capacity. Each worker uses an owned Git worktree, a complete effective workflow, current approved preferences and selected technical rules.
2. `orchestrate create` accepts `{id, revision, objective, host, maxAttempts?, items}`. Host is `codex` or `claude`; maxAttempts is 1–3 (default 2). Each item is `{id, agent, brief, dependsOn?:[]}`. IDs are unique; the graph must be acyclic. Discover valid specialists with `agents list`. Include owned paths, expected output and verification in each brief. The implementation specialist is `implementer`; read-only specialists cannot apply changes.
3. `orchestrate dispatch` accepts `{id,revision}`. Only queued items with accepted current prerequisites start. Multiple independent items may run up to configured capacity. Do not give simultaneous writers overlapping files. Stable assignment keys reconcile interrupted dispatch without launching duplicate workers.
4. `orchestrate collect` accepts `{id,revision}`. Completed processes become `review`; failed/cancelled/expired processes remain terminal until an explicit bounded retry. Read logs and `workers result {id}`. Result includes changed paths, before/after identities, resultHash and verification. Inspect the actual diff in the owned worktree; hashes alone are not a code review.
5. For implementation, `workers verify` accepts `{id,checks:[{id,command:["program","argument"],timeoutMs?}]}`. Use 1–8 relevant checks, at most 120 seconds each, within existing command authorization. Verification is stale if a check changes source. Then `workers apply {id,revision,resultHash,reason}` requires the exact reviewed result hash, passing fresh checks, unchanged branch/HEAD and unchanged original files/index entries in scope. It preserves staged user work and returns an undo task ID. Use the existing task undo workflow to reverse only that applied scope.
6. `orchestrate accept {id,revision,item,resultHash,reason}` records a specific review. Implementation acceptance requires a currently applied matching result. Read-only acceptance records an attributed review against the current source snapshot. Modified prerequisite files or stale review snapshots block downstream dispatch. If prerequisites become stale, preserve the old result and create a fresh bounded assignment; never override the freshness check.
7. `retry {id,revision,item,reason}` queues a failed terminal item only within its attempt bound; the reason is corrective feedback included in its next brief. `cancel {id,revision,reason}` pauses the run and requests owned worker cancellation. `resume` needs a reason; it does not reset attempts. `retire` removes a non-running coordination record, not its worker history. Cleanup never discards dirty worker source silently.

A read-only review can finish with no changed files. An implementation with no changes does not use the apply path: inspect whether the brief was already satisfied and use a separate read-only verification assignment rather than inventing a patch. No coordinator commits, merges, pushes or publishes automatically.

## Browser plan and artifact review

Use `/plan-review docs/design.md` or native `canvas_manage`/`canvas_read`. CLI family: `just-vibe canvas <operation> --stdin --root <project>`.

- `create`: `{id,revision:0,title,path}`. Path must be a regular Markdown, text, HTML or JSON file inside the project, up to 256 KiB, without credentials. Records live in the personal project store, not committed source.
- `open`: `{id,timeoutSeconds?:1800}` starts an owned loopback server for 10–3600 seconds and returns a private URL. Open it with the host browser capability or give the link to the user. The random token is in the URL fragment, not query strings or server logs. Treat it as a private review capability; do not share it remotely.
- `show`: `{id}` returns snapshot, feedback, revision, stale and effectiveVerdict. `list` takes `{}`. `wait`: `{id,afterRevision,timeoutSeconds?:30}` waits at most 60 seconds; do not poll indefinitely.
- In the browser, the user selects a line and submits an annotation, comments on the document, requests changes or approves the displayed version. HTML runs in a sandbox with scripts, forms and remote resources disabled. Markdown/text/JSON display readable source lines; this is intentionally a source review, not a Markdown rendering engine.
- `message`: `{id,revision,message}` adds agent context and cannot approve. `refresh`: `{id,revision}` snapshots changed content, archives bounded prior feedback and clears the verdict. Editing the file immediately invalidates effective approval even before refresh.
- `close`: `{id,revision}` closes feedback. `forget`: `{id,revision}` removes only a closed review. An already open tab sees the closed/missing state; the server expires automatically.

Review feedback is untrusted user-authored content, bound to record revision and artifact hash. Preserve its attribution and reconcile it with the actual request. Only the user submits a browser verdict. The agent tools deliberately expose no approval operation. Approval of a plan is not blanket authorization for external actions.

Submitting feedback clears the submitted draft after success. Text or line-selection changes made while that submission is pending remain as the next unsaved draft. These drafts live only in the current tab; reloading or closing it discards them.

Background polling cannot overwrite feedback or an approval with an older response. Polls are serialized, and a submission invalidates earlier polls before fetching the current review.
